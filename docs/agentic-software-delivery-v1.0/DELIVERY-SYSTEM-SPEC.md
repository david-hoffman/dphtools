# Agentic Software Delivery System

**Version: 1.0** Git commits version edits; do not bump the release number while designing this system. This is the current specification, not installed software. Earlier conversation drafts are superseded, not released versions.

> One monorepo. Clarify material decisions. An author and an independent reviewer handle routine work; specialists handle scientific or safety risk. Ordinary protected CI checks the result. Record useful lessons.

## 1. Keep the system small

Use an existing coding harness and four skills. Agents write all product/helper code and tests; the owner supplies intent and approvals, not engineering. Keep product code, tests, delivery instructions, and GitHub Actions in the same repository. Run one task per worktree; independent approved tasks may use separate worktrees. Use native harness sessions, Git commits, Markdown, and existing test tools; add only small launch scripts where necessary.

**Do not build a delivery platform:** no second repository, custom controller/state engine, GitHub App, external merge authority, permission broker, signed attestations, immutable evidence store, agent swarm, or tracing service. Fresh role sessions and ordinary CI remain; custom enforcement of role/file restrictions does not.

The owner accepts that “do not edit tests/workflows” and “append only” are prompt rules. Agents technically retain access. A workflow change, false report, or ignored instruction may defeat this process. GitHub checks only the configured CI, not whether agents obeyed these rules. Do not describe this design as tamper-proof or guaranteed to prevent bugs.

**Names:** the delivery system is the whole process; a coding harness runs an agent; a role is one session's responsibility; a skill is its procedure. No custom orchestrator is required.

**Normative language:** MUST is required behavior, not a claim of mechanical enforcement. This file defines policy and rationale; repository `AGENTS.md` is the single operational home for shared instructions. Skills contain role-specific procedures and refer to that home. Supporting prompts and generation templates must agree; they are not additional live rulebooks.

## 2. Setup and architecture intake

Start read-only. Inspect existing instructions, manifests, interfaces, tests, and documentation. Before proposing remediation, produce a small baseline inventory: existing failures, exact measured statement/branch coverage and its scope, environment/tooling problems, and unresolved behavior. Identify the revision, environment, and commands behind the evidence; label stale results. Use existing checks in a usable isolated environment, keeping generated reports temporary and leaving product/tooling files unchanged. If measurement is blocked, report it as unknown with the blocker and proposed measurement step. Do not run downloaded or repository setup scripts just to discover the project.

| Starting point | Route |
|---|---|
| Usable, owner-approved architecture exists | Reuse it. `docs/PROJECT.md` may simply link existing canonical documents. |
| Empty repository, no architecture | Interview the owner about the first useful outcome and constraints; propose a small architecture record. |
| Existing code, no usable architecture | Describe observed structure, ask what is intended, and resolve material gaps. Do not assume existing behavior is correct. |
| Architecture is unapproved, contradictory, or affected by this task | Reconcile only the affected decisions, then obtain approval. |

Architecture intake produces one short `docs/PROJECT.md`, using [the template](templates/PROJECT.md): purpose, constraints, stack, component responsibilities, public interfaces, verification commands, and operation. Prefer one deployable component. Markdown is sufficient; diagrams are optional. Link actual schemas instead of copying them. Architecture approval does not approve every future task.

Infer languages/frameworks from evidence in an existing monorepo. For an empty one, recommend a stack from the owner's requirements and obtain approval. Do not prescribe a product language because the coding harness uses it.

Choose current, coherent ecosystem tooling from primary documentation: one formatter, lint/static checks, native tests and coverage, dependency locking, and suitable security checks. Preserve sound existing choices. For example, a Python project might use Black plus Ruff linting and fast pre-commit hooks; this is an example, not a universal prescription. Repeat necessary checks in CI. Pin dependencies/actions appropriately; do not install competing tools.

Setup is the explicit exception that may create initial workflows and test infrastructure. Show the plan before applying it, separating delivery-tooling installation from existing-product remediation, with expected effort, measurement gaps, and required owner decisions for each. Installation approval does not approve product repairs or settle numerical behavior. In a repository without a commit, an authorized metadata-only initial commit may establish `main`; do not put an untested application there. A minimal callable scaffold may support the first tests, but label missing-feature evidence honestly.

Repeating setup inspects and completes approved gaps; it does not overwrite working conventions. Missing architecture prevents A or product implementation, but not read-only discovery or approved setup. Retain the 100% requirement. The owner chooses how to bring an existing project into the system case by case; this specification prescribes no automatic remediation sequence. Expose substantial baseline maintenance, missing contracts, and dependencies that would prevent a proposed task from passing full verification before approving that work. Installed tooling does not make a failing/under-covered product ready.

## 3. Step 0: clarify and approve each task

Use the same `intake` skill for architecture and tasks. Before task delivery, check the architecture route above. Reuse answers rather than repeating interviews.

Read the request, then ask about decisions that affect behavior, scope, interfaces, permissions, data, errors, cost, or acceptance. Usually ask up to three high-value questions per turn. Challenge vague answers using concrete alternatives. Recommend a simple default but get agreement; never infer consent from silence. Stop questioning settled or irrelevant future details.

The target is **no unresolved material ambiguity**, not a guarantee of zero ambiguity. A complete authorized request can proceed with a meaningful read-back; do not ask again for approval already supplied. Internal implementation choices can remain delegated.

Reuse the established contract and existing task/PR record for routine maintenance; do not require a new document or specialist for every assertion. For new behavior needing a contract, use [the template](templates/TASK.md). Capture observable requirements with stable IDs, non-goals, public interfaces, positive/error/boundary examples, allowed scope, checks, risk, and a preparation/execution budget. Each expected result must follow from approved behavior, an applicable primary reference, or a mathematical invariant. Unspecified units, conventions, and estimator choices return to intake; coverage requirements do not resolve them. A reference or invariant must apply to the approved interface, not silently select missing behavior. For a bug, separate observed behavior, expected behavior, reproduction evidence, and root-cause hypotheses. An uncertain bug can receive an approved, bounded investigation; its output is a report, not a speculative fix.

For a large request, intake creates a **slice plan** at `docs/tasks/<plan-id>.md`, linking each necessary contract, observable end-to-end outcome, dependencies, budget, and completion condition. Each slice is a task with one candidate PR and, on the specialist route, one reviewed checkpoint lineage; do not create parallel A/B pairs inside a larger implementation task. Dependent slices wait for completed prerequisites to enter their baseline; independent slices may use separate tasks/worktrees. Each planned slice must meet the complete verification/coverage merge gate at its intended baseline. If a shared baseline gap makes that infeasible, return that adoption decision to the owner instead of promising a sequence that cannot finish.

New contracts default to at most **five scenarios per slice**; the owner may explicitly approve a larger coherent slice. Count distinct input/context and observable-outcome cases in the Contract scenario table, not test functions or assertions. Do not hide distinct error/boundary cases in one row to evade the limit. The author supplies the mapping and the independent reviewer verifies it; on the specialist route these are A and B. Extra test data exercising the same approved case need not create new scenarios; a new material behavior returns to intake.

Present the exact draft, or the slice plan and all slice contracts in one read-back. Record the owner's explicit approval in the conversation or GitHub discussion, identifying the approved documents/revision. Approved later slices need no repeat interview. Redistribution of unchanged approved scenarios into smaller slices needs no new approval if behavior, interfaces, dependencies, permissions, and total budget stay within the plan; record the mapping and inherited allowances. Other material changes return to intake and renew affected tests/reviews. No custom approval service or hash-signing protocol; agents must not fabricate approval.

Intake drafts examples, not the executable test suite. Give each author/reviewer a narrow packet with only relevant context. Specialist A/B receive approved behavior, public contracts, approved fixtures, and test conventions—not interview transcripts, patches, private design hypotheses, or implementation notes.

## 4. Proportional delivery and independent review

Classify by changed behavior and lost proof, not patch size. Routine maintenance and features with established correctness contracts use an author and one fresh independent reviewer. The author may change authorized product, tests, documentation, and infrastructure together; use meaningful existing tests and add focused public-entry-point checks for changed behavior or missing proof. The reviewer independently examines expectations, behavior, scope, evidence, security, and simplicity; it must not fix a candidate and approve its own repair. Use separate A/B/C/D only for genuine scientific or safety risk: new numerical contracts or custom correctness oracles, release/publication safety, or other material behavior/security risk. Escalate when that risk emerges. An infrastructure change is not automatically scientific or safety risk; identify the actual lost proof.

Routine work needs no blind specialist test checkpoint. Keep its relevant contract, baseline/check evidence, candidate, review, and correction history in the existing task/PR. Changes to routine tests/fixtures need independent review; specialist changes follow the checkpoint routing below.

### Specialist A/B/C/D

| Role | Work and completion condition | Restrictions by instruction |
|---|---|---|
| **A: test author** | Return behavior-focused tests, requirement/expectation sources, and classified baseline results, or a specific contract blocker. Prefer end-to-end tests. | Do not inspect implementation, its history, the learning log, or implementation conversations. |
| **B: test reviewer** | Accept an identified test revision or return concrete test defects/contract gaps, including oracle review. | Same blind inputs as A, plus A's tests. Return corrections to A; do not implement. |
| **C: implementer** | Return the smallest necessary product change (possibly none), candidate commit, and check results, or a classified blocker. | Do not change tests, fixtures, snapshots, coverage/discovery settings, workflows, delivery rules, or unrelated interfaces. |
| **D: final reviewer** | Accept the exact passing candidate or return evidenced findings on correctness, security, scope, and simplicity. | Do not fix the candidate and approve the same repair. Do not inherit C's conversation. |

Start a fresh independent reviewer session using the harness's supported controls; use fresh root sessions for specialist A/B/C/D. Do not simulate specialist independence in one chat or fork the author's conversation for review. Disable avoidable inherited memory where supported. A/B receive only a narrow input packet and are instructed not to browse other files. Before their public-API probes or test runs, configure warning and traceback rendering without implementation source excerpts; preserve diagnostic categories/messages, failure counts, and exit status. In Python, pytest's `--tb=no` alone is insufficient: warnings also need source-free formatting. Disclose accidental source exposure in the handoff; a later clean run does not restore that session's blindness. No custom filesystem isolation is required; independence is procedural, not guaranteed. Repository instructions cannot override mandatory host progress updates or create unavailable event-wait tools. Use native completion facilities when present and bounded status checks otherwise; keep raw logs outside Git and report concise structured results.

Give each role a narrow packet identifying the approved slice/scenarios, permitted inputs, relevant test/candidate revision, requested output, completion condition, budget, and remaining review/repair allowances. Keep related cases in the slice's checkpoint; do not launch another role cycle for each assertion or uncovered line. The observing role records a failure's category and evidence; uncertain causes need bounded diagnosis before the coordinator routes work. Classification grants no permission to edit another role's files.

A **test oracle** is the rule deciding whether a result is correct. B reviews that decision logic as well as the assertions. For custom numerical or plotting oracles, use small distinguishing examples to show that the rule accepts legitimate alternatives and rejects plausible wrong results. Check parsers/observers, units, tolerances, and allowed outcomes against the contract; do not repair malformed output in the oracle or invent a stopping priority. Use this existing B review, not another reviewer role or a mandatory mutation-testing platform.

After two B reviews without acceptance, B diagnoses the blocker before another A rewrite. Contract ambiguity goes to intake with the specific ambiguity and a recommended clarification; excessive slice scope gets proposed split points. A split that only redistributes approved scenarios follows section 3's existing approval. If neither remedy resolves the finding, report the concrete blocker rather than inventing ambiguity, escalating models, or continuing an automatic retry loop. Section 9 defines when review rounds may restart and which allowances must carry over.

After B accepts the tests, run them against the approved baseline. Existing-code, remediation, and regression tests may pass on their first run; record the approved behavior they confirm. Do not manufacture a failure, mutate product code to prove sensitivity, or require an unnecessary C edit. A claimed reproduced bug needs a valid test reaching the intended behavior and failing for the approved reason. A first-project scaffold establishes feature absence, not reproduction of an old bug. Before any repair cycle, classify the failure and route it:

| Failure category | Next action and checkpoint consequence |
|---|---|
| Environment/tooling failure | Diagnose through authorized setup/maintenance, then resume and rerun affected checks. Dependency/import/fixture setup failures alone establish no product defect. Unchanged specialist tests keep their checkpoint; changed tests/fixtures need independent review on the selected route. |
| Test defect | Routine author corrects authorized tests with renewed independent review. Specialist work uses fresh A/B, a revised checkpoint, and valid baseline evidence before C resumes; C never repairs tests. |
| Product defect | With valid evidence and approved behavior, route to the authorized routine author or fresh specialist C, then applicable checks and fresh independent review. Unchanged specialist tests retain their checkpoint. |
| Unresolved requirement | Return the affected decision to intake. After approval, renew affected tests/review; specialist work renews A/B and the checkpoint before C. Coverage pressure supplies no approval. |

An unclassified failure needs bounded diagnosis before a product repair. Record mixed causes separately. A failure to follow an existing rule is an execution error, not automatically a missing rule.

Commit the reviewed tests and record that commit in the task. This is the **test checkpoint**, frozen by convention—not read-only storage. Then start C. A branch without an open PR may be pushed as a backup, including a failing checkpoint; record its incomplete status. This is not submission or readiness evidence. If tests are wrong or incomplete, follow the routing above. Label tests written after implementation as supplemental, never as original test-first evidence.

Run meaningful focused checks and the highest required project verification tier before opening/reopening a routine PR (including a draft) or updating it. Known failures and incomplete required-domain coverage remain blockers; unknown CI results are pending, not success. For this project, the owner-approved six-tier [verification contract](../tasks/LOCAL-VERIFICATION-CONTRACT.md#verification-hierarchy) selects fast prose, library, doctor, release tooling, full, or release preparation. Use conservative base/candidate classification; shared infrastructure/build inputs, spanning domains, add/delete/rename, unavailable/changed base, or uncertainty select full. Explicit domain runs prove their scope, not PR classification. Full local verification remains the reference path for integration, diagnosis, Tier 5, and any stronger approved risk/check plan. Specialist scientific/safety work normally includes full local reference verification before submission; record an approved narrower plan and its limits if applicable. Record candidate, command, environment, and result outside the tracked candidate and keep it unchanged during applicable checks and review. Rerun invalidated evidence, including changes to tests, dependencies, environment, or integration base. Backups are labeled incomplete and confer no readiness. The independent reviewer checks meaningful assertions, actual behavior, evidence, and applicable editing restrictions. Report violations and restore the intended baseline before continuing.

One bounded specialist implementation repair after the initial C attempt may use fresh C and D; section 9 defines its accounting. A change of requirements or tests repeats affected work on the selected route, whether or not a PR exists yet. Keep one concise **Current state** section in the task document or its linked PR/discussion: approvals, route, candidate commit, reviewed checkpoint where applicable, review/check results, blockers, next action, and one metrics line with scenario count, author/reviewer launches, specialist A/B rounds and C repairs where applicable, and budget use where measurable. Record a final candidate's own identity and results outside its tracked tree, in the conversation or PR; prepare the pointer before verification. Keep no competing status copies or edits merely to record a verified commit's own hash. Replace superseded status; Git preserves history. Link evidence rather than repeating handoffs; full logs remain outside Git. Only lesson entries in `LESSONS/` require append-only treatment. No separate evidence database or mandatory commit-trailer scheme.

Merge only the unchanged independently reviewed candidate after complete required platform CI and verified native required-check protection under section 6. Merge must be authorized by the owner; authorization may already be supplied for the task. A further code change needs renewed applicable checks/review. Do not bypass failures. Record release impact and draft notes, including compatibility/migration needs, in the task contract. Publication requires separate explicit owner approval of the frozen bundle under the project release policy and section 6.

## 5. End-to-end first, not end-to-end only

**Coverage is primarily earned by exercising useful behavior through the real entry point.** For a web app, run important browser journeys through the real application/backend and a disposable test database. For a CLI, run its executable and inspect outputs, exit codes, and files. For a service or library, use its public API and observable effects; do not invent a browser layer.

For each changed requirement, start with the smallest realistic success, failure, and boundary scenarios. Assert the outcome, not merely that a mock was called, a file contains a string, or the application compiles. Trace expected results to the contract/reference/invariant required by section 3, never the implementation being tested. Contract-supported invariants may test part of a behavior while an absolute interpretation remains unresolved; record that limit rather than claiming full behavioral validation. Do not duplicate every end-to-end assertion with unit tests. These choices borrow pstack's [behavior](REFERENCES.md#r2--test-behavior-not-implementation) and [real-artifact](REFERENCES.md#r3--verify-the-real-artifact) emphasis, and, for browser projects, [Playwright's user-visible testing guidance](REFERENCES.md#r8--end-to-end-testing-practice).

Use integration or unit tests for a genuine gap: difficult error injection, combinatorial logic, or a branch that would make a whole-system test slow or brittle. No unit-test quota or fixed test-type percentage. Do not forbid valid negative assertions or property tests just because a heuristic dislikes them.

A behavioral test is implementation-coupled when a refactor preserving its approved observable contract would break the test. Test interfaces that production code or real callers also need; do not require production exports, wrappers, or injection hooks solely for tests. D investigates code referenced only by tests, while recognizing that a public library API may serve external callers. An explicit public, platform, or architectural contract can justify a structural check; suspicion alone is not authority to delete an existing test. These judgment criteria adapt [OpenClaw's test audit](REFERENCES.md#r10--openclaw-test-audit), not its implementation-reading workflow.

The independent reviewer (B on the specialist route) rejects execution solely to raise coverage without a meaningful correctness check; negative tests passing because an unrelated validation rejected the input; fixtures that supply the result whose production behavior is supposedly tested; and test names claiming more than their inputs exercise. A check need not use a literal assertion statement: an expected exception or successful completion may itself be approved observable behavior. Require the intended path and outcome, not a particular assertion syntax.

A chooses and explains numerical tolerances from the approved algorithm description, applicable references, conditioning/error bounds, and arithmetic precision available in the blind packet. Identify absolute/relative comparisons and relevant scales. B checks both that legitimate numerical variation passes and that plausible wrong values fail. Do not inspect implementation to derive tolerances, tune them to candidate output, or relax an explicit accuracy contract. Missing behavior still returns to intake; choosing a justified test tolerance does not itself require a new owner accuracy specification.

Test owned components together where practical. Stub uncontrollable external services at their boundary, document what is not exercised, and use an approved provider sandbox check where integration correctness requires it. Do not mock the internal path whose behavior is the requirement. Use synthetic data, isolated state, readiness checks rather than fixed sleeps, and bounded waits. A suite that fails and then passes on retry still needs investigation; do not hide flakiness.

Require exact **100% measured statement and branch coverage** across every complete owned domain required by the approved verification plan whenever that domain runs. This project's owner-approved hierarchy replaces global coverage on every PR with exact required-domain coverage; canonical full and release preparation retain fresh global/per-package 100% measurement. Instrument relevant subprocesses, servers, and browser code; a passing browser test alone does not measure backend coverage. Include never-imported files and whole shared files with their required test closure. Inspect exact metrics, not rounded display values. Scoped evidence cannot claim unexecuted domains or cached results as fresh.

Narrow documented exclusions may cover vendor, generated, or non-executable files—not inconvenient handwritten branches. Missing/unsupported coverage is a reported gap, never fabricated success. Do not reduce the threshold through `doctor`. Complete measured coverage is not proof of complete behavior. Use existing tools and the test review; no mandatory mutation-testing platform.

## 6. Ordinary GitHub CI

Use the monorepo's ordinary GitHub Actions workflow. This project retains Linux/macOS/Windows and a stable required aggregate named `ci-required`. Seal the conservative plan for the exact PR candidate and comparison base. Tier 1 requires fresh fast results on all three platforms; runtime tiers require the complete selected tests and exact 100% whole-owned-domain statements/branches on each platform. Full plans retain fresh global/per-package coverage. Keep every underlying result and selected scope visible, and aggregate each operating system separately. All assigned nodes execute exactly once. Missing, failed, blocked, skipped, foreign, scope-mismatched, or incomplete evidence cannot satisfy the gate. `ci-required` always runs, including Tier 1; no skipped gate or custom gate publisher/GitHub App.

Apply section 4's focused submission checks and highest required project tier. Fast local hooks provide feedback on commits and pushes; preserve existing hooks and configuration. A blanket full pre-push gate must not prevent permitted pre-PR backups. No custom PR-state controller is required; hooks are bypassable feedback. CI verifies the sealed selected plan for the submitted candidate on the complete supported platform matrix; local success does not certify other platforms. Report failures honestly and route newly discovered failures under section 4.

CI should install locked dependencies, run the selected quality/types/audit/build steps, verify actual wheel/source-distribution installs, run the complete selected tests/coverage, and retain useful failure reports. Collection without a comparison base defaults to full; shards/aggregation inherit the sealed manifest scope and cannot narrow it. Fail on failed commands, empty test discovery, unexpected skipped/focused tests, and missing required reports using native tools where available. Do not use `continue-on-error` or path filters that silently remove required validation. Keep diagnostic output short with access to full logs.

Configure native protection for this project's routine PR target `codex-main`: PRs, required `ci-required`, current branches, and no ordinary force-push/deletion or bypass. Preserve production `main` protections and release approval settings. Read back the actual API/settings configuration before relying on CI as the authoritative merge gate; an unavailable permission/API is a merge blocker, not verified enforcement. Report configuration inspection separately from an observed enforcement demonstration on a real PR. [GitHub setup](GITHUB-SETUP.md) explains actions and capability limits. GitHub accepts some skipped/neutral conclusions, so `ci-required` must actually run and reject incomplete prerequisites ([source](REFERENCES.md#r7--github-protected-branches)). Native CI completion/auto-merge facilities may be used only after protection is established and merge is owner-authorized.

**Workflow/test editing restrictions are prompts, not engineering.** Routine authors may change authorized tests/infrastructure; specialist A/B own authorized tests and specialist C may not change restricted files. Setup or explicit maintenance scope may change infrastructure. CI executes repository-controlled files and cannot independently prove these restrictions were respected. There is no anti-tampering certification.

Use ordinary CI secret hygiene: no production secrets in test runs, no secrets committed, and only necessary token permissions. A local hook is feedback, not a substitute for required CI.

### Release preparation and publication

Installing release automation follows the same approved infrastructure scope, independent review, and verification rules as other delivery tooling. Operating the installed process does not require repeating feature-development roles. The project record defines the owner-selected release source, version/channel policy, destinations, commands, required platforms, completion checks, and recovery instructions; these are not universal defaults. A PR target does not determine the release source. An owner release request authorizes preparation, not publication.

Resolve the eligible source once and freeze the commit, version, trusted workflow/helper revision, originating run/artifact identity, destinations, notes, and file hashes. Run canonical fresh full verification, including exact global/per-package coverage regardless of the PR tier, on all required platforms with the release version, then check the retained artifacts' metadata and clean installation outside the source checkout. Present this evidence and any compatibility limits before explicit owner approval of publication. An ordinary merge or tag push is not that approval. Publish those exact files without rebuilding; identity changes require renewed preparation and approval. Recheck source eligibility and bundle identity before publishing without silently moving the candidate when its source branch advances.

Use ordinary Actions and a protected publication environment, with write permissions and registry credentials limited to jobs that need them. Keep candidate execution out of the privileged publisher. Download and verify published file hashes before installation checks in jobs without publication credentials, then finalize the release only after the project's completion checks pass. Resume partial publication from the retained bundle, recognize matching published files, upload only absent files, and stop on conflicts or ambiguous state. Missing retained artifacts require fresh preparation and approval. Native reruns may require renewed environment review; never bypass it. Document actual registry trust and environment configuration, retention limits, and unapplied setup; local checks cannot prove hosted protections exist.

## 7. A small append-only learning log

Setup creates root `LESSONS/` with a `README.md` format guide. Store each lesson in a separate Markdown file so independent tasks add different files instead of editing a shared log or index. Use `YYYYMMDDTHHMMSSZ-<task>-<role>-<short-slug>.md`, with the file's creation time in Coordinated Universal Time (UTC). The timestamp is not the time of the observed event. Never overwrite a filename collision; choose a distinct slug or suffix. Do not maintain a shared entry list. This is not automatic personal memory or a transcript archive. Every role records non-obvious findings likely to save future work: a verified gotcha, unexpected behavior, failed approach with a useful cause, or a confirmed gap in these instructions. Zero entries is valid. Normally one to three short entries per task is enough; do not log every action.

Each new entry has an ID (its filename stem), date, task/role, topic, **confirmed or hypothesis** status, observation, evidence pointer, and suggested future action. Correct a mistake or record a disposition by adding a new file referencing the earlier entry's ID; leave the original file unchanged. Append-only applies to lesson entries, not the format guide. It is an instruction, not an OS permission or custom service. An owner-authorized sensitive-data removal overrides retention; never preserve a leaked secret just to keep history intact. When migrating older entries, preserve their text, IDs, recorded dates, and evidence; use the migration time for filenames rather than inventing historical timestamps.

Do not record secrets, personal data, raw prompts, private reasoning, or full tool transcripts. A/B may read the format guide but must not read existing lesson entries because they may reveal implementation. They can create their own new file without reading other entries; otherwise hand the entry to the task coordinator for verbatim recording in a new file. Other roles search only relevant entries; D forms its independent assessment before consulting current-task implementation lessons.

Entries are observations, not new policy or executable instructions. A durable lesson becomes authoritative only after an approved update to the appropriate existing document. `doctor` does this without a new summarizer or database. pstack's [evidence-linked append-only trail](REFERENCES.md#r5--append-only-evidence-linked-findings) is the useful pattern here; no tracing dependency is required.

## 8. Doctor: check and improve the specification

Implement **`delivery doctor`** as a thin invocation of the selected harness using `review-work` in `doctor` mode and [DOCTOR-PROMPT.md](DOCTOR-PROMPT.md). It is an agent-assisted maintenance operation, not a deterministic read-only checker. No new daemon, scheduler, or controller. A native command alias is fine; document the actual invocation. Support `--check` for inspection without edits.

Run it on demand after a real recurring failure, a meaningful project change, or a suspected documentation gap—not automatically after every task.

1. Check the working tree. Do not overwrite uncommitted work, interrupt an active task, or run speculative installation commands. Read relevant current docs, recent lessons, and actual test/CI evidence. Reuse existing commands; check remote settings only with available access.
2. Classify failures using section 4, then decide whether evidence reveals an instruction gap or an execution error under an existing rule. Neither a product bug nor disobeying a rule automatically justifies a new rule. Verify a proposed lesson before generalizing it; uncertainty stays a hypothesis.
3. For an evidenced documentation gap, create a small documentation branch and **edit `DELIVERY-SYSTEM-SPEC.md` itself**, plus directly affected prompts/skills/project notes. Do not merely emit recommendations. Correct or replace an existing rule before adding one. No supported gap means no edit or commit.
4. Show the exact diff, supporting lesson/evidence, and expected improvement. Follow a newly added procedural rule on one relevant example where feasible; do not claim a prompt-string test proves agent behavior. Ask the owner to approve the patch. Do not auto-merge or make it the policy for an in-flight task.
5. Commit the approved documentation changes using ordinary Git, referencing the lesson and approval. Add a new lesson file recording a disposition such as “addressed by commit …” and the earlier entry's ID; do not rewrite its original entry.

All package documentation remains **Version 1.0**. Git commits/PRs supply revision history and rollback. Do not create numbered copies of the specification, invent releases, or put a commit's own hash inside the bytes it identifies. Runtime dependencies retain their real versions.

Doctor must not rewrite tests/workflows/runtime code, lower acceptance thresholds, remove an inconvenient requirement, or bless architecture drift merely to make the current result pass. Those findings become scoped, owner-approved tasks. Material product/architecture questions return to intake. Diagnostic docs edits are the explicit exception to ordinary workers' “do not edit the spec” rule; the limits are still instructions, not enforced permissions.

## 9. Cost and completion

One active task per worktree and one intake read-back for material approvals not already supplied. Routine work uses an author and a fresh independent reviewer; genuine scientific/safety risk uses four specialist roles. Reuse approved contracts and relevant context. On the specialist route, default to two A/B review rounds per review window and at most one corrective implementation cycle after initial C. One round is B's completed review of an identified A test revision. Acceptance closes that window. A later evidenced, authorized test/requirement correction under section 4 opens a new window; record why the checkpoint is reopened and retain prior rounds. A new conversation or resubmission alone opens no window.

After two nonacceptances in a window, stop rewrites for B's diagnosis under section 4. Restart a two-round window only when B confirms the diagnosed ambiguity or scope problem was addressed by approved clarification or a genuine split; otherwise request an explicit disposition/extension. Record the resolution and prior rounds. Renaming work, replacing a checkpoint, or continuing the same rejected tests does not qualify. No new window erases history, spent budget, or used C repairs.

Keep C's repair allowance separate from A/B rounds. Replacement checkpoints, renamed tasks, and splits inherit the used C allowance and consumed budget for the same work; allocate the parent's remaining allowance across children rather than multiplying it. A planned new slice is distinct work; relabeling a correction to an earlier slice is not. Further C repairs require an explicit owner-approved extension. All preparation, diagnosis, review, environment/test corrections, and failed attempts count toward the task and plan budgets, even when A/B rounds legitimately restart. Stop at the budget limit. Use native limits where available; disclose missing metering rather than promise a hard financial cap.

Load the narrow role packet, relevant interfaces, and selected skill; reuse context rather than loading this whole package, archives, or lessons every turn. Use deterministic commands for routine checks. Rerun when candidate, test, dependency, environment, integration-base changes, required platforms, or unresolved evidence justify it; reuse valid evidence only for matching inputs. An unchanged commit alone does not settle an environment failure. Evidence reuse cannot replace complete required platform CI or release preparation with a partial receipt. Keep shared operational instructions in native `AGENTS.md` and its template; skills carry role-specific differences. No log-summarizer models or automatic context optimizers. Host-required progress updates remain mandatory; unavailable event-wait tools remain unavailable. Doctor may use recorded scenario counts and outcomes to propose an owner-approved size-limit change; five is a starting limit, not a proven optimum.

Before calling setup usable, demonstrate: architecture routing on an empty/existing project; baseline inventory and owner-chosen remediation scope; material clarification/authorization; one routine author/fresh-reviewer path with focused/cheap checks and a genuine-risk specialist path when applicable (reuse relevant historical evidence, or label it not applicable); actual native `ci-required` protection readback; one normal passing PR with complete platform verification; a lesson file and a doctor-generated spec diff.
