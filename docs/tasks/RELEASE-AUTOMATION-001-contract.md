## Public behavior

The repository is `david-hoffman/dphtools`. Release packages are `dphtools`. Production sources are resolved from `main` only. A valid version is canonical, unprefixed, three-component Python packaging version text: a stable `MAJOR.MINOR.PATCH` or an `aN`, `bN`, or `rcN` prerelease of that form. Stable versions select PyPI; prereleases select TestPyPI. Reject malformed, prefixed, development, local, postrelease, and noncanonical spellings. Examples `1.0.0` and `1.0.0rc1` are test data, not an actual release request.

`python tools/delivery release prepare --version VERSION [--ref main]` dispatches `.github/workflows/make_release.yml` on trusted `main`, with the selected version as input, and returns the exact resulting run URL/identity. GitHub's versioned workflow-dispatch API returns that identity; never infer the newest run from a list. `--ref` defaults to `main`; any other value is rejected before dispatch. Optional `--resume RUN_ID` requests the same retained bundle from an earlier release run instead of rebuilding it. Positive decimal run IDs only. `python tools/delivery release status --run RUN_ID` reads that exact run and reports its URL, status, and conclusion; it performs no dispatch, approval, or mutation. A missing executable, API failure, malformed response, wrong repository/workflow/source identity, or unsuccessful completed run cannot be reported as successful. Status may report pending/running work without treating it as completed success. Preserve the existing `delivery doctor` behavior.

The following deterministic worker command interfaces are consumed by the workflow and may be invoked for local diagnosis. They must not perform publishing or approve deployments:

- `python tools/release.py version VERSION`: validate and print JSON with `version` and `channel` (`pypi` or `testpypi`).
- `python tools/release.py manifest --version VERSION --source-sha SHA --workflow-sha SHA --run-id RUN_ID --dist DIR --reports DIR --notes FILE --output FILE`: validate a release bundle and successful three-platform full-verification evidence, then write its manifest. SHA values are complete lowercase 40-digit hexadecimal commit identities. Distribution input contains exactly one wheel and one `.tar.gz` source distribution. Both contain valid package metadata for `dphtools`, agree with VERSION, retain the declared Python requirement and package dependencies, and contain no unsafe archive member paths. Required platforms are `ubuntu-24.04`, `macos-15`, `windows-2025`. Each platform directory beneath reports contains exactly one canonical `checks.json` for mode `full`, with no failed/missing steps and zero return codes for formatting, lint, docstrings, types, audit, build, install, coverage erase/tests/combine/json/xml/report, and report validation. Reject missing, malformed, unsuccessful, ambiguous, or incomplete evidence. The workflow remains responsible for establishing those reports' source identity through its pinned job inputs and dependencies.
- `python tools/release.py check --manifest FILE --dist DIR`: validate the manifest and retained files, including exact filenames, sizes, SHA-256 digests, version/channel, package metadata, and source/workflow/run identity fields. Missing, extra, modified, unsafe, duplicate, or mismatched package files fail. It does not rebuild or modify distribution files.
- `python tools/release.py smoke --manifest FILE --dist DIR`: first validate the bundle, then install each distribution into its own clean disposable environment outside the checkout. Run dependency consistency and installed-version/import-origin checks. Exercise the existing public imports and a simple approved public behavior: summing a 2x2 array containing 0,1,2,3 through `dphtools.utils.bin_ndarray(..., new_shape=(1,1), operation='sum')` returns 6. Package `__version__` and installed metadata agree with the manifest. Source-distribution installation must run with the Git executable unavailable and without repository Git metadata. This preserves the approved proposal's clean source-installation requirement. Use noninteractive Matplotlib. A subprocess or assertion failure is failure; retain useful diagnostics. No registry credentials are needed.
- `python tools/release.py reconcile --manifest FILE --dist DIR --output DIR [--require-complete]`: read the selected registry's version JSON, compare every published filename/digest with the manifest, and verify any downloaded published bytes. A genuine version-not-found response means no published files; other HTTP/transport/parse failures do not. Stage only absent files from the validated retained bundle in an initially empty output directory. Reject mismatching or unexpected registry files. `--require-complete` fails if either expected file is absent. No overwrite, upload, generic duplicate suppression, or rebuild occurs. An existing nonempty staging directory is rejected rather than trusted. Registry URLs are HTTPS URLs belonging to the selected PyPI/TestPyPI service; untrusted metadata must not fetch arbitrary local/private endpoints.

Manifest JSON is a workflow artifact, not an authorization token. Required fields: `schema_version` = 1; `repository`; `version`; `channel`; `source_ref` = `refs/heads/main`; `source_sha`; `workflow_sha`; positive integer `run_id`; `files` (two records with `filename`, nonnegative integer `size`, lowercase 64-digit `sha256`); `verification` (the three platform names mapped to report SHA-256 digests); and `notes` (release-note text). Store no credential or self-referential manifest hash. The caller can hash the finished manifest separately. Error paths return a nonzero status and a useful diagnostic. Exact wording and internal Python symbols are not contractual.

Retain exact 100% statement/branch measurement for owned Python runtime and relevant subprocesses; shell/YAML execution is not measured by coverage.py. Before PR submission, require a passing full run on the exact committed candidate; CI repeats configured platforms. Baseline full verification passed for unchanged runtime at `e557c7d` with pending documentation edits: 1,232 tests, 2,094 measured statements, 544 branches, zero missing, 185 warnings. This is preparation evidence, not final candidate certification.

Workflow stages must bind package SHA, trusted workflow/helper SHA, version, originating run/artifact identity, and hashes. Preserve report artifacts on failure. Use retained Linux-produced release distributions; other matrix build copies are verification inputs only. Versioneer sees a temporary local release tag before building; no public tag exists until the owner-approved stage. Do not retarget an approved bundle when main advances. Main-only publication is enforced both in workflow eligibility and environment configuration where available. Native reruns may require renewed environment review; do not bypass it. Real GitHub environment and registry identity verification is a separate setup check, not proven by mocks.
