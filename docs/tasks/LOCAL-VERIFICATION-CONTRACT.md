# Local verification

**Version 2.0** Setup infrastructure authorized by the owner; proportional delivery and the revised submission/merge distinction are authorized by [DELIVERY-EFFICIENCY-001](DELIVERY-EFFICIENCY-001.md). No new numerical behavior is approved here.

## Public behavior

- The invoking interpreter selects the environment. Verification requires Python >=3.10 and the applicable exact versions in `requirements-dev.lock`; product package metadata still declares Python >=3.8. Commands locate the repository from the script, so invocation does not depend on the caller's current directory.
- `python tools/verification.py preflight` checks interpreter operation, applicable locked dependency versions, and imports. It creates a disposable copied-child environment using `venv.EnvBuilder(with_pip=True)`, executes that child's interpreter and pip, installs a tiny local wheel without network access, and imports the installed probe. This exercises the copied-launcher boundary used by installation observers and catches broken environments that a symlink-only probe can miss. It does not modify the system interpreter.
- `python tools/verification.py fast` checks Black formatting at 99 columns, the retained Flake8 critical-error selection, and NumPy docstring style throughout owned `dphtools` submodules. These independent cheap checks continue after another cheap check fails.
- `python tools/verification.py full` uses up to eight bounded local test subprocesses; `full --workers 1` retains the serial reference path. It runs preflight, fast checks, configured type checks, locked dependency audit, distribution build/install, complete tests/doctests, and coverage combination/reporting. Build waits for successful preflight and quality prerequisites. Installation requires a successful build and exactly one wheel from that invocation. Installation failure blocks tests. A stale artifact or separate source rebuild does not verify the build output.
- Coverage processing may continue after failed tests only when this run produced fresh data. Failed tests remain failed even when their diagnostic coverage reports succeed. Missing data blocks dependent coverage commands; an old report cannot fill an interrupted run. Full verification requires exact 100% measured statements and branches for all owned runtime files, including never-imported files and all handwritten verification helpers. Only the repository's generated `dphtools/_version.py` remains omitted.
- Missing or invalid mode/options return exit 2. Success returns 0; any failed or blocked step or invalid report returns 1. An operating-system launch failure retains its diagnostic and blocks dependent expensive steps while independent checks continue. Importing the Python verification module must not launch tools or create run reports.
- Commands stream combined child stdout/stderr to the console and each step's UTF-8 log while the child is running. Undecodable bytes are represented visibly, and the actual child status remains authoritative. A local success verifies the selected interpreter/platform; CI verifies Linux, macOS, and Windows separately.
- Each invocation creates a fresh directory under `reports/verification/`, or uses an explicitly supplied empty `--report-dir`. It identifies that directory immediately. Full mode retains `pytest.xml`, `coverage.json`, and `coverage.xml`; sharded modes retain their manifests, execution receipts, and raw parent/child coverage data. Existing reports cannot establish success for a new invocation.
- Full verification rejects missing, malformed, empty, skipped, failed, or errored test results. It rejects missing/malformed coverage reports, absent owned files, disabled branch measurement, exclusions, and any exact missing statement or branch count. Rounded percentages do not establish completeness. Zero instrumentable branch opportunities are allowed and are not a claim about every logical path.
- Coverage must actually instrument executed Python files at every owned directory depth, as well as report never-imported files. For example, executed modules under `dphtools/subpkg/`, `dphtools/utils/subpkg/`, and `tools/subpkg/` contribute their covered statements. The generated omission applies only to the repository's `dphtools/_version.py`; an identically named handwritten file elsewhere is still measured. Git shell-hook statement/branch measurement remains unsupported by coverage.py and is disclosed.

## Receipts and input identity

`checks.json` uses document version `2.0`. The verifier writes an initial receipt and atomically replaces it after each completed step. During work, `complete` is `false` and `outcome` is `incomplete`; only finalization sets `complete` to `true` and `outcome` to `passed` or `failed`. An interrupted or partial receipt cannot establish passing evidence.

Each step records its name, command when applicable, state (`passed`, `failed`, `blocked`, or `reused`), return code for an executed operation, monotonic `duration_seconds`, dependency names, blocking reasons, declared input identity/digest, and retained log path/SHA-256. A blocked or reused step has no new child exit status. The receipt includes mode, interpreter, platform, failed-step names, identity/digest, and `receipt_digest`, which hashes the complete record excluding that digest field. Consumers verify the seal and retained bytes rather than accept a success label alone.

Identity binds source/test/configuration/lock bytes, interpreter executable and version, installed dependency versions, platform and coverage settings, and verifier check version. Recognized pydocstyle configuration files at the root and every ancestor are included because the command inherits that configuration implicitly. The local environment includes a digest of ambient environment variables without exposing their values. Build/install inputs also bind artifact bytes and Versioneer's actual Git revision, tags, reachable history, shallow state, dirty state, and version result. Portable shard identity retains relevant platform/Python/dependency/source inputs while separating local executable paths and host-specific ambient details; it does not pool operating systems.

## Isolated CI commands

Run collection once per required operating system, then run all assigned shards with separate checkouts, interpreters, installations, temporary paths, and empty report directories. The public CLI defaults to two shards:

```sh
python tools/verification.py collect --report-dir reports/verification/collect --manifest reports/verification/collect/manifest.json
python tools/verification.py shard --manifest reports/incoming/collection/manifest.json --shard-index 0 --shard-count 2 --report-dir reports/verification/shard-0
python tools/verification.py shard --manifest reports/incoming/collection/manifest.json --shard-index 1 --shard-count 2 --report-dir reports/verification/shard-1
python tools/verification.py aggregate --manifest reports/incoming/collection/manifest.json --shards reports/incoming/shard-0 reports/incoming/shard-1 --report-dir reports/verification/aggregate
```

Every pytest collection/execution invocation uses an absolute cache directory inside its private report directory. Collection runs preflight and quality/build checks, freezes the real pytest/doctest node IDs, and assigns every node exactly once to nonempty shards. `--shard-count` supports 2, 4, 5, 7, 8 or 10; collection seals the count in its manifest, and shard/aggregate commands must request that same count. Optional `--durations PATH [PATH ...]` uses validated retained duration records to balance assignments. Both machine and local worker partitions select advisory weights for the current operating system when supplied, with universal records as fallback. Optional affinity groups intersect the actual selection and keep unique consumers together; stale, overlapping or empty hints cannot omit nodes. If too few batches remain for the required nonempty count, singleton scheduling takes precedence. Shared-fixture estimates charge module setup once plus consumer call/teardown costs. Serial resource groups preserve each independent node's full setup/call/teardown estimate. Shards verify the frozen collection, install the retained wheel, and record each assigned test's completed setup/call/teardown and actual parent/child coverage. Aggregation rejects absent, duplicate, failed, partial, foreign-platform, mismatched, or changed evidence before combining coverage and applying the same exact owned-source/report gate as `full`. Immutable collection artifacts are copied between jobs; mutable installation environments are private. `shard --workers N` can subdivide its assigned nodes among at most eight local subprocesses without changing its machine assignment or pooling platforms.

The hosted workflow uses five Linux machines with four local workers, five macOS machines with three workers, and ten Windows machines with three workers (twenty machines total). A separately logged idle wait targets a common start 180 seconds after collection completes; late starts remain in the complete test-command window. Total workflow and runner time include waiting. Collection, shards and aggregation pin Python 3.10.21 on Linux and 3.10.11 on macOS/Windows and use the same sealed platform count and retain every shard artifact. Runner CPU capacity is recorded in the job log; hosted timing must measure the complete suite execution window rather than infer it from an individual worker's duration.

## Explicit evidence reuse

`python tools/verification.py fast --reuse /absolute/path/to/checks.json` opts into an audited whitelist containing only `docstrings`. Formatting and lint still execute. `full`, collection, shards, aggregation, audit, build/install, and test proofs run fresh; `--reuse` with a mode other than `fast` is a usage error.

A normal `fast` run records the identifiable runtime bytes needed by later reuse even when no receipt is supplied. Reuse requires the exact unchanged command/inputs, a complete successful original `fast` receipt containing the expected three passed checks, valid identity/receipt seals, and unchanged retained logs. The runtime identity rechecks interpreter, standard-library, and installed-environment files. Uncontrolled `PYTHONPATH`/`PYTHONHOME`, user-site imports, or other unidentifiable imports prevent reuse. Invalid, missing, failed, blocked, incomplete, or changed evidence records a rejection and runs the check fresh. A reused step records original receipt/command/input/log provenance and its current validation duration; it does not relabel an old command as newly executed.

## Maintenance measurements

`python tools/verification_metrics.py /absolute/path/to/tasks.json` reads explicit task records and prints a deterministic JSON summary with metrics document version `1.0`. Input is a JSON list; each record has a unique nonempty `task_id`, a nonempty `comparable_group`, and `cohort` equal to `reference` or `candidate`. Optional `controlled_comparison` is boolean, and `receipts` is a list of retained receipt paths resolved relative to the input file. The same receipt invocation cannot be counted twice.

Task measurements are `time_to_pr_seconds`, `time_to_merge_seconds`, `agent_launches`, `runner_seconds`, `model_tokens`, and `defects`. Values are finite nonnegative numbers or `null`; absent/unavailable measurements remain unknown. Validated complete receipts supply executed/reused/blocked/repeated check counts and their actual monotonic durations. Repetition means an executed check with the same name and input digest appeared earlier in that task's evidence. Reuse-validation duration is measured separately from the original command duration and is not itself an estimate of time saved.

Summaries retain known/missing counts, totals, means, and paired-group mean differences. Only groups with both reference and candidate tasks support comparisons. Comparisons are marked estimated unless all their records declare a controlled comparison. The pilot remains incomplete until at least ten comparable unique task records exist; synthetic fixture records, a test-count reduction, or an unpaired benchmark do not demonstrate completed maintenance-task gains.

## Ordinary local Git hooks

- `.githooks/pre-commit` runs fast checks before a commit. It rejects unstaged tracked changes so the files checked correspond to the staged tracked content.
- `.githooks/pre-push` requires a clean working tree, including ordinary untracked files, and requires every non-deletion source revision being pushed to equal the checked-out commit. It then runs fast verification once and rejects the push on fast-check failure. A failure confined to full verification does not block a permitted pre-PR backup when fast and Git-state checks pass. It must not contact the remote itself or determine PR state.
- Both hooks select `${DPHTOOLS_PYTHON:-python}` as the interpreter. Missing/broken tools fail visibly. Existing hooks/configuration must be inspected before installation and preserved if present.
- After successful verification, recheck the relevant Git state before allowing the operation: commit must still check the same staged content with no unstaged tracked edits; push must still have the same HEAD and a clean tracked/untracked checkout. A save or tool write during checks invalidates that result. This detects ordinary stale results; it is not an atomic snapshot or a guarantee against concurrent changes.
- Hooks are ordinary bypassable feedback, not permission enforcement or certification. Routine PR opening/reopening (including drafts) and updates require meaningful focused checks plus `fast` on the exact committed candidate. Known failures, including known incomplete coverage, remain visible blockers; pending platform CI is not a passing result. Use `full` as the local/reference path for integration, diagnosis, and high-risk work when its approved risk/check plan requires it, rather than before every routine PR. Record candidate, commands, environment, and results outside the tracked candidate and keep it unchanged through applicable checks/review. Rerun invalidated evidence after candidate/test/dependency/environment/base changes. A branch without an open PR may back up a failing checkpoint, explicitly labeled incomplete; that backup is not readiness evidence. No failing PR is published merely to demonstrate the gate.
- Merge requires fresh independent review, the unchanged reviewed candidate, complete Linux/macOS/Windows verification, and exact 100% owned statement/branch coverage. The stable `ci-required` aggregate is authoritative only after actual native required-check protection on `codex-main` is read back and verified. Missing/unavailable protection blocks reliance on that gate and must be reported; local `full` cannot replace the platform matrix. Preserve production `main` protections and separate frozen-bundle publication approval. Native CI completion/auto-merge requires verified protection and existing owner merge authorization.

## Independent test scope

Test the real command/hook entry points. Controlled external-tool stand-ins are appropriate for deterministic failure/report cases; do not replace the verifier under test or mock a numerical algorithm. Temporary fixture repositories must be isolated from this checkout and require no network or remote push. Exercise a real local Git push only to a temporary local bare repository when useful.

These are tests added during setup, not retroactive original test-first evidence. Routine authorized maintenance uses an author and one fresh independent reviewer. When genuine scientific/safety risk requires specialist A/B, they may read this contract, existing delivery-command tests for platform fixture conventions, and their own tests; they must not inspect verifier/hook implementation, source history, other sessions, or private gap lists. Copying executable bytes opaquely into an isolated fixture is allowed. Preserve existing product/doctor tests and all runtime/configuration files outside approved maintenance scope.

## Full-suite worker execution

Local workers share the unchanged checkout and locked interpreter after the verifier completes build/installation. Every worker owns its pytest base directory, operating-system temporary directory, Matplotlib cache, log/receipt directory and absolute coverage-data family. Scratch directories live outside the checkout and are cleaned after execution; logs, receipts and raw coverage remain in the report directory, including in hosted shard artifacts. Worker subprocesses disable import bytecode writes to avoid mutating the shared runtime while reuse checks fingerprint it. Native numerical thread pools use one thread per worker to prevent nested oversubscription.

The parent collects the complete pytest/doctest node set, balances every node exactly once using advisory durations, and waits for all launched workers. Each worker verifies the full collection before executing only its assigned nodes. The parent validates sealed successful worker receipts, actual exit statuses, one successful setup/call/teardown per assigned node, JUnit counts and fresh parent/child coverage before reporting success. Missing, duplicate, foreign, skipped or failed execution fails the test step. Available fresh coverage remains diagnostic data after failure. The exact owned-source/report gate remains unchanged.

The serial reference command also validates its sealed collection and completed execution before reporting success. A successful pytest exit and complete coverage cannot substitute for execution of every collected node.

Runtime fingerprints continue to bind the same sorted file hashes and directory aliases and read fresh bytes on every invocation. Directory-entry traversal and one bounded reader for substantial file reads avoid nested reader oversubscription. Declined identities cancel queued reads; successful identities still hash every actual file. No metadata or prior-run cache replaces byte checks.
