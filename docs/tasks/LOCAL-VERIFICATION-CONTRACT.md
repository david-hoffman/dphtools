# Local verification

**Version 1.0** Git tracks revisions. Setup infrastructure and proportional delivery are owner-authorized. [VERIFICATION-HIERARCHY-001](VERIFICATION-HIERARCHY-001.md) records approval of the six trigger tiers and exact required-domain coverage in place of global coverage on every PR. Canonical full and release preparation retain fresh global/per-package 100% coverage. No new numerical behavior is approved here.

## Verification hierarchy

The owner approved six trigger tiers. The highest applicable trigger wins. The verifier selects tests and complete owned domains, not convenient changed lines. A higher tier may have a different domain closure; use the table, not an assumption that every suite contains all lower-tier tests.

| Tier | Trigger | Required evidence |
|---|---|---|
| 1: fast | Prose-only edits outside build inputs, examples, and delivery policy. | Fresh `fast` plus meaningful focused checks for the changed content. No runtime coverage claim. |
| 2: library | Changes confined to known library behavior/tests, with no import, module-initialization, dependency, version, installation, or subprocess impact. | Preflight, quality, types, locked dependency audit, build, clean smoke installs of the actual wheel and source distribution, all library tests/doctests, and exact 100% library-domain statement/branch coverage with report validation. |
| 3: doctor | Known doctor-only prompt/contract or test changes with no shared-runtime or infrastructure effect. | Library evidence plus all doctor tests and the shared-dependency tests needed for complete coverage of the entire owned doctor domain. |
| 4: release tooling | Known release-only helper/test changes that do not alter shared infrastructure or release policy/approval controls. | Library evidence plus all release tests and shared-dependency closure, including doctor tests needed to cover the entire shared delivery file. This is tooling verification, not release preparation or publication approval. |
| 5: full | Shared runtime/infrastructure, verification/coverage/CI, dependencies, packaging, fixtures, examples, delivery/release policy, spanning domains, or uncertain changes. Root README, manifests, metadata, requirements, and Versioneer inputs are build inputs. | Canonical fresh unsharded full locally or equivalent complete sealed native CI: all tests/doctests, real artifact smoke installs, and fresh exact 100% owned statements/branches globally and per package. |
| 6: release preparation | Owner requests preparation of a release. | Canonical fresh full on every required platform, frozen source/version/workflow/destinations/metadata/hashes, and clean installation checks of the exact retained artifacts before the existing explicit owner publication approval. |

Library ownership includes every handwritten `dphtools/**/*.py`, including never-imported modules. The doctor domain adds the entire `tools/delivery`; its test closure includes `tests/test_delivery.py` and `tests/test_release_cli.py`. The release domain adds `tools/release.py`, `tools/release_workflow.py`, and `tools/release_probe.py` to library and shared delivery ownership, with all release tests and doctor tests required by that closure. The remaining handwritten verification helpers require full. The existing generated `dphtools/_version.py` omission remains the sole generated runtime omission; no new coverage exclusions are introduced.

Automatic narrowing supports a deliberately small syntax set: unchanged exact known top-level imports and initialization, plain undecorated function headers, and bodies containing only literal expressions in returns/assertions, docstrings and `pass`. Bodies using names, calls, attributes, indexing, conditional/local imports, context managers, control flow or other unsupported execution require full. Module assignments must use literal values and plain name targets. Scientific API and helper-heavy files therefore often require full even when an author expects a narrower impact. The installed doctor prompt carries shared delivery and approval policy, so it requires full. Explicit domain commands remain available for local development and establish only their reported scope.

A checked-in inventory assigns every known test to a domain. Ownership changes, unknown files or unassigned tests, add/delete/rename, dirty inputs, unavailable or changed comparison bases, import/module-initialization/dependency/version/install/subprocess changes, shared `tools/delivery` edits, and ambiguous or mixed-domain changes conservatively require full. Do not infer a safe domain solely from a filename or turn uncertainty into a narrower plan. The classifier records the base and candidate identity, changed paths, selected tier/mode, owned domains, test closure, and promotion reasons.

```sh
python tools/verification.py fast
python tools/verification.py library
python tools/verification.py doctor
python tools/verification.py release
python tools/verification.py full
python tools/verification.py classify --base BASE
python tools/verification.py pr --base BASE
```

Explicit domain commands establish only their stated scope. `classify` emits the plan without running checks; `pr` classifies and runs the required mode against the same base/candidate. Missing or invalid bases cannot establish narrow evidence. Focused checks supplement these modes; they never replace the selected complete test/domain closure. Known failures remain blockers. No stale reports, skipped required tests, exclusions, or cached results count as fresh tier evidence.

## Public behavior

- The invoking interpreter selects the environment. Verification requires Python >=3.10 and the applicable exact versions in `requirements-dev.lock`; product package metadata still declares Python >=3.8. Commands locate the repository from the script, so invocation does not depend on the caller's current directory.
- `python tools/verification.py preflight` checks interpreter operation, applicable locked dependency versions, and imports. It creates a disposable copied-child environment using `venv.EnvBuilder(with_pip=True)`, executes that child's interpreter and pip, installs a tiny local wheel without network access, and imports the installed probe. This exercises the copied-launcher boundary used by installation observers and catches broken environments that a symlink-only probe can miss. It does not modify the system interpreter.
- `python tools/verification.py fast` checks Black formatting at 99 columns, the retained Flake8 critical-error selection, and NumPy docstring style throughout owned `dphtools` submodules. These independent cheap checks continue after another cheap check fails.
- `library`, `doctor`, and `release` run the complete selected tests and owned-domain closure above. `full` remains the unsharded local/reference path and runs all tests/doctests. Every runtime mode runs preflight, fast checks, configured types, the locked dependency audit, distribution build/install, and coverage combination/report validation. Build waits for successful preflight and quality prerequisites. Installation requires successful current build output with exactly one wheel and one source distribution. Smoke checks install each retained artifact in a clean disposable environment outside the source checkout and exercise the installed library. Installing from the source distribution uses that exact archive; substituting the checkout or a separate source rebuild does not verify it. Installation failure blocks tests. A stale artifact cannot verify this invocation.
- Coverage processing may continue after failed tests only when this run produced fresh data. Failed tests remain failed even when their diagnostic coverage reports succeed. Missing data blocks dependent coverage commands; an old report cannot fill an interrupted run. Every runtime mode requires exact 100% measured statements and branches for every file in its complete selected owned domains, including never-imported files and copied subprocesses. Full includes all handwritten verification helpers and retains exact global/per-package 100% coverage. Only the repository's generated `dphtools/_version.py` remains omitted.
- Missing or invalid mode/options return exit 2. Success returns 0; any failed or blocked step or invalid report returns 1. An operating-system launch failure retains its diagnostic and blocks dependent expensive steps while independent checks continue. Importing the Python verification module must not launch tools or create run reports.
- Commands stream combined child stdout/stderr to the console and each step's UTF-8 log while the child is running. Undecodable bytes are represented visibly, and the actual child status remains authoritative. A local success verifies the selected interpreter/platform; CI verifies Linux, macOS, and Windows separately.
- Each invocation creates a fresh directory under `reports/verification/`, or uses an explicitly supplied empty `--report-dir`. It identifies that directory immediately. Runtime modes retain `pytest.xml`, `coverage.json`, and `coverage.xml`; sharded modes retain their sealed scope/manifests, execution receipts, and raw parent/child coverage data. Existing reports cannot establish success for a new invocation.
- Every runtime mode rejects missing, malformed, empty, skipped, failed, or errored required test results. It rejects missing/malformed coverage reports, absent required owned files, disabled branch measurement, exclusions, and any exact missing statement or branch count in its declared domains. Rounded percentages do not establish completeness. Zero instrumentable branch opportunities are allowed and are not a claim about every logical path.
- Coverage must actually instrument executed Python files at every owned directory depth, as well as report never-imported files. For example, executed modules under `dphtools/subpkg/`, `dphtools/utils/subpkg/`, and `tools/subpkg/` contribute their covered statements. The generated omission applies only to the repository's `dphtools/_version.py`; an identically named handwritten file elsewhere is still measured. Git shell-hook statement/branch measurement remains unsupported by coverage.py and is disclosed.

## Receipts and input identity

`checks.json` uses document version `2.0`. The verifier writes an initial receipt and atomically replaces it after each completed step. During work, `complete` is `false` and `outcome` is `incomplete`; only finalization sets `complete` to `true` and `outcome` to `passed` or `failed`. An interrupted or partial receipt cannot establish passing evidence.

Each step records its name, command when applicable, state (`passed`, `failed`, `blocked`, or `reused`), return code for an executed operation, monotonic `duration_seconds`, dependency names, blocking reasons, declared input identity/digest, and retained log path/SHA-256. A blocked or reused step has no new child exit status. The receipt includes mode, selected tier/owned domains/test closure and base/candidate plan identity when applicable, interpreter, platform, failed-step names, identity/digest, and `receipt_digest`, which hashes the complete record excluding that digest field. Consumers verify the seal and retained bytes rather than accept a success label alone.

Identity binds source/test/configuration/lock bytes, interpreter executable and version, installed dependency versions, platform and coverage settings, and verifier check version. Recognized pydocstyle configuration files at the root and every ancestor are included because the command inherits that configuration implicitly. The local environment includes a digest of ambient environment variables without exposing their values. Build/install inputs also bind artifact bytes and Versioneer's actual Git revision, tags, reachable history, shallow state, dirty state, and version result. Portable shard identity retains relevant platform/Python/dependency/source inputs while separating local executable paths and host-specific ambient details; it does not pool operating systems.

## Isolated CI commands

Native CI seals one classification plan for the exact PR candidate and comparison base. Tier 1 runs fresh fast checks on Linux/macOS/Windows and `ci-required` explicitly requires their complete successful results; focused content evidence remains separately recorded. For runtime tiers, run collection once per required operating system using that same selected plan, then run both assigned workers with separate checkouts, interpreters, installations, temporary paths, and empty report directories:

```sh
python tools/verification.py collect --base BASE --report-dir reports/verification/collect --manifest reports/verification/collect/manifest.json
python tools/verification.py shard --manifest reports/incoming/collection/manifest.json --shard-index 0 --shard-count 2 --report-dir reports/verification/shard-0
python tools/verification.py shard --manifest reports/incoming/collection/manifest.json --shard-index 1 --shard-count 2 --report-dir reports/verification/shard-1
python tools/verification.py aggregate --manifest reports/incoming/collection/manifest.json --shards reports/incoming/shard-0 reports/incoming/shard-1 --report-dir reports/verification/aggregate
```

Without `--base`, collection defaults to full; release preparation explicitly selects full. With a base, collection conservatively classifies and seals the tier, mode, comparison/candidate identities, complete owned-domain closure, and real selected pytest/doctest node IDs. Each operating system must agree with the native plan. Collection runs preflight and quality/build/artifact-install checks, then assigns every selected node exactly once to two nonempty shards. Optional `--durations PATH [PATH ...]` uses validated retained duration records only to balance assignments, never to omit tests or count old evidence as fresh. Shards and aggregation inherit the sealed manifest scope; they cannot select a weaker scope. Shards verify the frozen collection, install the retained wheel, and record each assigned test's completed setup/call/teardown and actual parent/child coverage. Aggregation rejects absent, duplicate, failed, skipped, partial, foreign-platform, mismatched, or changed evidence before combining coverage and applying the exact whole-domain report gate. Full manifests retain the global/per-package gate. Immutable collection artifacts are copied between jobs; mutable installation environments are private. CI summaries state selected tier, domains, tests, and platform results; a selected domain run does not claim unexecuted domains or platforms. `ci-required` always runs and rejects missing prerequisites; workflow path skips or neutral results cannot satisfy it.

## Explicit evidence reuse

`python tools/verification.py fast --reuse /absolute/path/to/checks.json` opts into an audited whitelist containing only `docstrings`. Formatting and lint still execute. `library`, `doctor`, `release`, `pr`, `full`, collection, shards, aggregation, audit, build/install, and test proofs run fresh; `--reuse` with a mode other than `fast` is a usage error.

A normal `fast` run records the identifiable runtime bytes needed by later reuse even when no receipt is supplied. Reuse requires the exact unchanged command/inputs, a complete successful original `fast` receipt containing the expected three passed checks, valid identity/receipt seals, and unchanged retained logs. The runtime identity rechecks interpreter, standard-library, and installed-environment files. Uncontrolled `PYTHONPATH`/`PYTHONHOME`, user-site imports, or other unidentifiable imports prevent reuse. Invalid, missing, failed, blocked, incomplete, or changed evidence records a rejection and runs the check fresh. A reused step records original receipt/command/input/log provenance and its current validation duration; it does not relabel an old command as newly executed.

## Maintenance measurements

`python tools/verification_metrics.py /absolute/path/to/tasks.json` reads explicit task records and prints a deterministic JSON summary with metrics document version `1.0`. Input is a JSON list; each record has a unique nonempty `task_id`, a nonempty `comparable_group`, and `cohort` equal to `reference` or `candidate`. Optional `controlled_comparison` is boolean, and `receipts` is a list of retained receipt paths resolved relative to the input file. The same receipt invocation cannot be counted twice.

Task measurements are `time_to_pr_seconds`, `time_to_merge_seconds`, `agent_launches`, `runner_seconds`, `model_tokens`, and `defects`. Values are finite nonnegative numbers or `null`; absent/unavailable measurements remain unknown. Validated complete receipts supply executed/reused/blocked/repeated check counts and their actual monotonic durations. Repetition means an executed check with the same name and input digest appeared earlier in that task's evidence. Reuse-validation duration is measured separately from the original command duration and is not itself an estimate of time saved.

Summaries retain known/missing counts, totals, means, and paired-group mean differences. Only groups with both reference and candidate tasks support comparisons. Comparisons are marked estimated unless all their records declare a controlled comparison. The pilot remains incomplete until at least ten comparable unique task records exist; synthetic fixture records, a test-count reduction, or an unpaired benchmark do not demonstrate completed maintenance-task gains.

## Ordinary local Git hooks

- `.githooks/pre-commit` runs fast checks before a commit. It rejects unstaged tracked changes so the files checked correspond to the staged tracked content.
- `.githooks/pre-push` requires a clean working tree, including ordinary untracked files, and requires every non-deletion source revision being pushed to equal the checked-out commit. It then runs fast verification once and rejects the push on fast-check failure. A failure confined to full verification does not block a permitted pre-PR backup when fast and Git-state checks pass. It must not contact the remote itself or determine PR state.
- Both hooks select `${DPHTOOLS_PYTHON:-python}` as the interpreter. Missing/broken tools fail visibly. Existing hooks/configuration must be inspected before installation and preserved if present.
- After successful verification, recheck the relevant Git state before allowing the operation: commit must still check the same staged content with no unstaged tracked edits; push must still have the same HEAD and a clean tracked/untracked checkout. A save or tool write during checks invalidates that result. This detects ordinary stale results; it is not an atomic snapshot or a guarantee against concurrent changes.
- Hooks are ordinary bypassable feedback, not permission enforcement or certification. Routine PR opening/reopening (including drafts) and updates require meaningful focused checks plus the highest required tier on the exact committed candidate. Hook success supplies fast feedback only; run `pr --base BASE` separately. Known failures and incomplete required-domain coverage remain visible blockers; pending platform CI is not a passing result. Use `full` for Tier 5, release preparation, integration/diagnosis, and any stronger approved risk/check plan. Record candidate, commands, environment, and results outside the tracked candidate and keep it unchanged through applicable checks/review. Rerun invalidated evidence after candidate/test/dependency/environment/base changes. A branch without an open PR may back up a failing checkpoint, explicitly labeled incomplete; that backup is not readiness evidence. No failing PR is published merely to demonstrate the gate.
- Merge requires fresh independent review, the unchanged reviewed candidate, and complete Linux/macOS/Windows verification of the sealed selected plan with exact 100% statements/branches in every required owned domain. Full plans retain fresh global/per-package 100% coverage. The stable `ci-required` aggregate is authoritative only after actual native required-check protection on `codex-main` is read back and verified. Missing/unavailable protection blocks reliance on that gate and must be reported; local `full` cannot replace the platform matrix. Preserve production `main` protections and separate frozen-bundle publication approval. Native CI completion/auto-merge requires verified protection and existing owner merge authorization.

## Independent test scope

Test the real command/hook entry points. Controlled external-tool stand-ins are appropriate for deterministic failure/report cases; do not replace the verifier under test or mock a numerical algorithm. Temporary fixture repositories must be isolated from this checkout and require no network or remote push. Exercise a real local Git push only to a temporary local bare repository when useful.

These are tests added during setup, not retroactive original test-first evidence. Routine authorized maintenance uses an author and one fresh independent reviewer. When genuine scientific/safety risk requires specialist A/B, they may read this contract, existing delivery-command tests for platform fixture conventions, and their own tests; they must not inspect verifier/hook implementation, source history, other sessions, or private gap lists. Copying executable bytes opaquely into an isolated fixture is allowed. Preserve existing product/doctor tests and all runtime/configuration files outside approved maintenance scope.

Release preparation consumes complete canonical version 2.0 full receipts only after checking their distinct required operating-system identities, seals, fresh passed steps, retained logs, all owned source files, and exact global reports. Scoped receipts cannot satisfy preparation. Legacy version 1.0 full report support remains for the retained original contract; current preparation generates fresh version 2.0 evidence. Publication still requires explicit approval of the frozen bundle.
