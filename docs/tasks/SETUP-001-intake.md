## Approved coverage decision: `fit_ztp`

The owner subsequently resolved the explicit estimator deferral as recorded below. The approved contract is conditional maximum likelihood for a nonempty, one-dimensional NumPy array of finite, positive integer-valued observations; integer-valued real floating storage is acceptable. Preserve the scalar-rate return and input values. Reject empty, nonfinite, nonpositive, fractional, boolean, complex and nonnumeric observations with `ValueError`.

Starting from the [Poisson probability mass function](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.poisson.html), conditioning on a positive observation gives `P(X=k | X>0) = lambda**k / (k! * (exp(lambda)-1))`, for positive integer `k`. Thus the negative log likelihood, up to an additive constant, is `n*log(exp(lambda)-1) - sum(x)*log(lambda)`. For sample mean greater than one, its unique finite optimum solves `lambda/(1-exp(-lambda)) = mean(x)` with `lambda>0`. This derivation is an independent mathematical recommendation, not an oracle copied from runtime output.

For `[1,1,2,4]`, the sample mean is 2 and the proposed rate is approximately **1.59362426**; an ordinary, untruncated Poisson fit instead gives 2. This distinction matters because zero observations are absent by design. For all-ones data, the likelihood has a supremum as the rate tends to zero, but no positive-rate maximum. After discussing this boundary, the owner selected **`ValueError` for all-ones data**. Do not return zero as a limiting fitted rate. An eligible numerical fit that cannot produce the finite scalar rate must raise `RuntimeError`, not return a nonfinite or unsuccessful estimate.

No uncertainty API, extra tuning parameter, negative-binomial estimator or other distribution is included. Fresh A/B must independently derive/review numerical and boundary tests before C repairs this function. The unlimited maintenance budget and default single implementation-repair limit remain; no failed checks may be pushed.

## Approved coverage decision: standalone `make_lambda`

The approved contract gives the existing `make_lambda(j, d0)` helper Moré's per-parameter scaling recurrence while preserving its two-argument signature. For a real finite Jacobian `j` with `m` rows and `n` parameter columns, return an `n` by `n` diagonal matrix with `D[i,i] = max(d0[i], norm(j[:,i], 2))`. Accept `d0` as either a finite nonnegative scalar, applied to every parameter, or a one-dimensional vector of `n` finite nonnegative previous scales. The scalar interpretation is the owner-selected compatibility policy; the paper specifies the recurrence, not this Python argument's forms.

For `j=diag(3,4,12)` and `d0=[5,2,6]`, return `diag(5,4,12)`. With scalar `d0=2`, return `diag(3,4,12)`. This compares each parameter with its own earlier scale, never with a neighboring parameter. All off-diagonal entries are zero; a zero column with zero previous scale has zero resulting scale. Preserve both inputs. Require a nonempty two-dimensional real numeric Jacobian and the scalar/vector shape above; invalid shapes, nonfinite values, negative scales, boolean, complex or nonnumeric inputs raise `ValueError`. If finite inputs require an unrepresentable resulting norm, report `RuntimeError` rather than returning nonfinite scaling.

Scientific basis: Moré, *The Levenberg–Marquardt Algorithm: Implementation and Theory*, section 6, equations (6.1)–(6.3), already researched in `reports/more-scaling-research/REPORT.md`; [primary archival record](https://digital.library.unt.edu/ark:/67531/metadc1448594/). The selected pages of the retained primary PDF were rechecked; this is not a new full-paper audit. A/B receive only the approved mathematical contract and public signature, not the source-analysis record.

This repairs only the existing standalone helper. Do not wire it into `lm` or `curve_fit`, change the Laurence–Chromy method, or implement an unsupported scaling/solver path. No approval is inferred from the coverage target.

## Pending coverage decisions: angles and coordinate uncertainties

These two questions have been presented after the standalone helper approval. They remain proposals until an actual answer; they do not change the earlier unresolved-choice record by themselves.

For `calc_angles`, the recommended convention is active, right-handed extrinsic x/y/z rotations on column vectors, with `R = Rz(z) @ Ry(y) @ Rx(x)`, returning the existing three-item `(x,y,z)` tuple in radians. For valid proper 3-by-3 rotation matrices, use principal x/z angles in `[-pi, pi]` and y in `[-pi/2, pi/2]`. A positive 90-degree z rotation maps the x basis vector to the y basis vector and returns `(0,0,pi/2)`. At gimbal lock, warn and set z to zero while preserving the represented matrix, matching [SciPy's documented extrinsic xyz convention](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.transform.Rotation.as_euler.html). The convention is an API choice, not a conclusion justified by existing formulas. This proposal does not select a policy for non-rotation matrices, new batched inputs or degrees.

For `calc_drift(weighted="coords")`, the recommended interpretation of `sigma_x` and `sigma_y` is per-observation coordinate standard errors in the same units as `x0` and `y0`, with strictly positive finite uncertainties for the selected valid cases. They are not point-spread-function widths or variances computed from each moving trajectory. With independent Gaussian coordinate errors, minimizing `sum((position_i - drift)**2 / sigma_i**2)` yields the per-frame weighted mean `sum(position_i/sigma_i**2) / sum(1/sigma_i**2)`. This is the weighted least-squares criterion described by [NIST](https://www.itl.nist.gov/div898/handbook/pmd/section4/pmd432.htm), specialized here to a constant drift at each frame. Before final recentering, positions 0 and 10 with standard errors 1 and 2 give 2 rather than the unweighted 5. Preserve the existing per-track mean removal, per-coordinate weighting, frame handling and final drift recentering. For two tracks `[0,2]` and `[0,10]` with constant uncertainties 1 and 2, the centered result is `[-1.8,1.8]`, versus unweighted `[-3,3]`. The question specifies the default x0/y0 schema; it does not silently choose uncertainty names for arbitrary coordinate labels, missing/nonpositive-uncertainty policy or a new mapping argument.
