## Proposed operating contract

1. **Request preparation.** Supply a version and resolve `main` to one commit once; record both identities. Reject `codex-main`, feature branches, and unmerged PR refs as publication sources. Draft release notes from merged changes since the previous release, including compatibility changes and known limits. The owner chooses the version; automation validates it. Ordinary merges and tag pushes do not publish packages.
2. **Prepare the release version.** In disposable checkouts with full tag/history information, create the proposed tag locally so Versioneer sees the final version. Do not push it yet. Use canonical unprefixed versions; `1.0.0` and `1.0.0rc1` illustrate the grammar, not an approved next version. Historical tags remain untouched. Parse versions with `packaging.version.Version`; accept the explicitly supported stable/prerelease forms, reject development/local/dirty versions, and require the parsed version to match the selected channel. [Version parsing reference](https://packaging.pypa.io/en/stable/version.html).
3. **Verify the actual candidate.** Run `python tools/verification.py full` against that commit and local release tag on the existing Linux/macOS/Windows matrix with the hashed verification lock. Preserve exact 100% measured statement/branch coverage and failure reporting. Missing, skipped, cancelled, or failed required work blocks readiness. A tag changes version-derived behavior even when source files are unchanged, so earlier branch CI is not enough by itself.
4. **Prepare and test the release files.** Select one wheel/source-distribution bundle built with the locked tools. Test installation of these retained files with pip in clean environments outside the checkout, assert their import locations and installed versions, check declared dependencies, and exercise representative existing public contracts. Test installation from the source archive without Git available. The final tag, wheel, archive, and installed package must agree. Canonical verification may build other test copies; only the identified release bundle is promoted.
5. **Present a complete approval summary.** Show version/channel, source commit and branch, change notes, required check links, package filenames and SHA-256 digests, installation results, compatibility gaps, and the exact registry destinations. Store the manifest and files as Actions artifacts associated with this workflow run. No remote Git tag, GitHub Release, TestPyPI upload, or production upload occurs before owner approval.
6. **Publish the approved files.** After approval, recheck source eligibility, tag/version availability, manifest identity, and file digests. A changed version, commit, required destination, or artifact bundle requires renewed preparation and approval. Create the remote tag at the recorded commit; upload the retained artifacts; install the published versions in fresh environments; then publish the GitHub Release with the same files and evidence links. Do not rebuild during publication. This separation follows the [Python packaging guide](https://packaging.python.org/en/latest/guides/publishing-package-distribution-releases-using-github-actions-ci-cd-workflows/).

Release branch, selected by the owner: `main` only. At preparation, record its resolved commit. At publication, require that commit still belongs to `main` and that release settings remain applicable; normal later commits do not silently retarget the release. A rewritten branch that removes the candidate blocks publication. `codex-main` remains available for exploratory integration and ordinary checks, but cannot authorize publication.

Production destination, selected by the owner: PyPI only. Completion requires both the wheel and source distribution to be published and their installation checks to pass, followed by GitHub Release finalization. Approved prerelease policy: explicit prereleases go to TestPyPI only. TestPyPI is not a mandatory dependency for every stable release. Moving a prerelease to a stable version requires a new bundle because the embedded version changes.

The package source ref is an input to the trusted installed workflow, not permission to select arbitrary publisher code from that ref. Record both the package commit and the workflow/helper revision in the manifest. Artifact downloads must identify the originating workflow run and artifact, not just a reusable filename.

Remove the Anaconda upload step, its dedicated publishing action and credential references, `conda.recipe/meta.yaml`, and the commented Anaconda/Conda badges in the README. Update the current release documentation. Retire a dedicated Anaconda publishing secret during activation after confirming it has no remaining use. Preserve `environment.yml`, verification interpreter paths, historical evidence, and historical published packages; none is needed to remove the release process. This owner decision supersedes the earlier proposal to repair Conda packaging and the project record's instruction to preserve that release recipe.

## Publication, permissions, and recovery

Use one protected publication job after all build and test jobs. That job consumes identified files and performs metadata checks and uploads; it does not install or execute the candidate library. Scope package-registry and GitHub write permissions to this stage. Serialize release publication and do not cancel a job in the middle of uploads.

Run post-upload installation checks in separate jobs without registry credentials, OIDC access, or GitHub write access. Download the published files and compare their digests with the approved manifest before installing them. A small finalization job with only the necessary GitHub permission publishes the GitHub Release after those checks succeed. All stages consume the same approved run and bundle identity. A native rerun may require another environment review; the harness must not bypass it. The design has one approval stage, not a guarantee that every recovery needs zero further clicks.

Use PyPI Trusted Publishing through OpenID Connect (OIDC), bound to the exact repository, top-level workflow filename, and protected environment. This replaces stored PyPI/TestPyPI API tokens with short-lived credentials. Give `id-token: write` only to the publisher. Keep the publisher in the top-level workflow even if verification becomes reusable. [PyPI configuration](https://docs.pypi.org/trusted-publishers/adding-a-publisher/), [publisher usage](https://docs.pypi.org/trusted-publishers/using-a-publisher/), [reusable-workflow limitation](https://github.com/pypa/gh-action-pypi-publish).

Require the owner as environment reviewer and disable administrator bypass where supported. For a solo maintainer, allow the requester to approve their own deployment; prohibiting self-review would prevent that workflow. Verify actual repository-plan support and settings rather than claiming the YAML alone enforces approval. [GitHub environment controls](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

Pin action revisions and deliberate build dependencies. Retain the publisher's default attestations, which identify the publishing workflow; they are not proof that tests passed. Keep test evidence separately linked. [PyPI attestations](https://docs.pypi.org/attestations/producing-attestations/).

| State | Required behavior |
|---|---|
| Verification or installation fails | Retain diagnostics; no publication; classify the failure through the existing four-way harness routing. |
| Owner rejects or approval never arrives | No external publication. Preparation artifacts may expire normally. |
| A required artifact/report is missing or has changed | Stop. A fresh bundle needs fresh approval; do not recreate files silently. |
| Version/tag already exists on first preparation | Reject the new release attempt. An explicit resume must identify the original run and bundle. |
| Upload result is uncertain or only some files reached a registry | Read the registry state. Matching filename and digest count as completed; absent files may be retried from the retained bundle. A different digest stops the run. Do not treat a generic duplicate-upload response as success. |
| The wheel reaches PyPI but the source-distribution upload fails | Report a partial release. Resume the missing file from the retained bundle; do not rebuild or overwrite the successful upload. |
| Both files and published-install checks succeed but GitHub Release creation fails | Resume finalization without republishing packages. |
| Published installation check finds a real defect | Mark the release failed/partial with evidence. Propose registry recovery and a corrected new version for owner action. Never force-move the release tag or claim Git rollback undoes publication. |

PyPI exposes file digests for reconciliation through its [JSON API](https://docs.pypi.org/api/json/). For a bad release, [yanking](https://docs.pypi.org/project-management/yanking/) is a registry action with different semantics from deletion or Git rollback. External service outages remain failures/pending results, not permission to skip evidence.

Use the workflow summary as the single current release status. The immutable preparation manifest identifies the approved bundle; later publication receipts record what actually happened. Attach the completed record to the GitHub Release. This is ordinary artifact/report storage, not an evidence database or approval-token service.
